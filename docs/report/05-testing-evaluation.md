# 5 Testing and Evaluation

This chapter covers how the system was tested and how it was evaluated. Testing, in 5.1, is about whether the parts behave as they should and, more than that, whether the system can be trusted not to make things up. Evaluation, in 5.2, is about the protocols and the metrics behind every number this report quotes, so the results in the next chapter can be read with confidence. The two are kept apart because they answer different questions: testing asks whether the code is correct and honest, and evaluation asks how good the models are and against what.

## 5.1 Testing

Testing here means three things. There are the ordinary automated tests that check the parts of the system work. There are a small number of special checks whose only job is to stop the system from fabricating a number or a piece of feedback. And there is a separate audit that asks whether the trained models are genuinely good or have simply memorised their training data. Each is described in turn.

The backend carries a broad automated test suite written with pytest. It covers the recommender from end to end, from the content filter's scoring against the program catalogue, through the plan adapter, to the chat intake, with the language model calls mocked so the tests are fast and deterministic. It covers the three form services, checking that each one builds, degrades gracefully when its weights are missing, applies the right per-error thresholds, and returns the raw schema with no invented fields, and it covers the serving endpoints, the benchmark catalogue's clip counts, and the path-traversal guard on the media endpoint. It also covers the offline metric and ensemble code that produced the headline numbers, the angular-feature geometry, and the configuration files that map exercises and defects. The Flutter app has its own smaller suite, 38 tests across 9 files, covering the data models, the benchmark filtering logic, and the result screens, including the states where there is no ground truth or no detected repetition. The nutrition engine is the one part without a dedicated unit-test file; it is checked at run time by its own verify step instead, described shortly.

Beyond the ordinary tests, a few checks exist for one reason only, to make fabrication impossible to ship unnoticed. The first lives in the evaluation notebook. Rather than have the headline F1 scores typed into the report by hand, the notebook recomputes all five of them from the raw per-clip score arrays at the stored validation-tuned threshold, and asserts that each one matches the saved result to within a millionth, so a headline number can not drift away from the data it claims to come from. The second checks the deployed models against those same saved results: a cross-check test runs the live serving path on sample clips and fails if the score it returns differs from the stored one by more than 0.02 for a video or 0.001 for an image, which proves that the model a user actually hits gives the same answer as the model that was evaluated. The third guards the feedback itself: a test scans the whole app for a list of banned severity and coaching words, the kind of confident language the system is forbidden from inventing, and fails if any of them appear in the code. The fourth guards the ground truth: the field that holds a clip's true label is read as a value that is absent when the dataset does not provide it, and is never quietly turned into a zero, with a test that asserts exactly this, so the app can never show an invented ground truth beside a model's guess.

Two deterministic verifiers sit inside the running system as well, and they are part of why the no-fabrication guarantee holds rather than being a hope. On the planning side, the plan validator counts a hard violation whenever a plan has the wrong number of training days, puts an exercise on the wrong kind of day, asks for equipment the user lacks, or includes a movement that clashes with an injury, and its repair step fixes these using only exercises from the dataset pool, never inventing one. On the nutrition side, the meal verifier re-checks every meal against the user's allergens and diet as a strict pass-or-fail gate, and the planner's critic refuses to award a good score to a plan that fails it. The calorie and macronutrient numbers do not need a gate of their own, because they are computed by formula and the planner only ever selects inside them, but the verifier reports how closely the finished plan matches them so the match can be seen rather than assumed.

The last and most involved piece of testing is the overfitting audit, which exists because a model that scores well can still be a model that has memorised a few hundred training examples, and on a dataset this small that risk is real. The audit examines every trained form model, baseline and self-supervised, every seed and every error, along seven lines of evidence. It confirms that the stored headline scores reproduce from the raw per-clip scores; it reloads each model from its actual saved weights and re-runs the official evaluation to confirm the saved scores were not edited; it checks that each saved model was taken from before its validation loss began to rise; it measures the gap between validation and test performance, at both the tuned-threshold F1 and the threshold-free precision-recall area, with confidence intervals; it checks that a model fails the same way on validation and on test; it checks that the results are stable across seeds and that the self-supervised features did not collapse; and it measures the gap between training and test performance, which is where memorisation shows up.

**Figure 17. Re-evaluation from the saved weights.** *[Insert docs/figures/audit_reeval_certainty.png]*

Figure 17 shows the second of these lines of evidence, the load-bearing one. Every deployed model was reloaded from its saved weights and re-evaluated, and every score came back matching the stored result with a difference of zero, which means the numbers in this report are the numbers the saved models actually produce. The audit's overall verdict is that no deployed model shows validation-to-test overfitting: validation tracks test within sampling noise on every measure. The verdict is careful not to claim zero overfitting in the strict sense, because the two rarest errors, the inward-knee squat error and the elbow overhead-press error, do show a large gap between training and test performance, the mark of a model leaning on memorisation where there are only a few hundred positive examples to learn from. That gap is bounded, because validation still tracks test and the test scores still match the published work, and the self-supervised pretraining shrinks it. The detail of these gaps, and the figures that show them, belong with the results in Chapter 6.

## 5.2 Evaluation

The evaluation of every module follows one rule, already stated but worth repeating because it is the thing that makes the results comparable: each module is measured with the same metric, on the same official split, as the published work it is set against. This section explains those metrics and protocols, one module at a time, so the numbers in Chapter 6 can be read without ambiguity.

The form models are measured by the F1 score for each error, which is the metric the Fitness-AQA work reports. F1 is the harmonic mean of precision, the share of the model's positive calls that are correct, and recall, the share of the real errors the model catches, and it is the right choice here precisely because the errors are imbalanced: a model could reach a high plain accuracy on the rare inward-knee error by simply never calling it, and F1 refuses to reward that, because such a model would have zero recall. Each model is run on the dataset's official test split exactly as released, and the decision threshold that turns a probability into a yes or no is set beforehand on the validation split, never on the test split, so the reported F1 is not quietly tuned to the data it is reported on. The per-error scores are summarised per exercise as a macro average, which weights the rare and the common error equally rather than letting the common one dominate.

**Figure 18. Precision-recall for the squat errors.** *[Insert docs/figures/squat_pr_curves.png]*

Figure 18 shows the precision-recall picture for the squat, which sits behind the single F1 number. Each curve traces how precision trades against recall as the threshold moves, the marked point is the operating threshold chosen on the validation split, and the area under each curve, a single threshold-free score, is what the overfitting audit compares between validation and test so that the comparison does not depend on the chosen threshold. The same audit also reads the area under the receiver-operating curve, another threshold-free measure, for the same reason.

The recommender is measured the way He et al. measure neural collaborative filtering, by a leave-one-out protocol. For each of the 973 users one positive interaction is held out, and the model is asked to rank that held-out program against 99 programs the user did not interact with. Two numbers come from this. The hit rate at 10 is the fraction of users for whom the held-out program lands in the top 10 of the 100, a simple did-it-find-it measure. The normalised discounted cumulative gain at 10, a measure from the information-retrieval literature [36], is more demanding: it rewards the held-out program for ranking near the very top and discounts it as it falls down the list, so a model that puts the right answer first scores higher than one that merely sneaks it into tenth place. As Section 4.1 set out, both numbers are computed on the synthetic interaction data, so they show how faithfully the model reconstructs the synthetic pattern and are not a claim about real-world recommendation quality.

The nutrition module is evaluated in two parts, for its two very different jobs. The recipe-text generator is measured with the same three families of metric the recipe-generation paper reports. BLEU [37] measures how much of the generated text's short word sequences appear in the real instructions, reported at one-word and four-word lengths, so a higher score means the wording is closer to a real recipe. ROUGE [38] measures the overlap the other way round, how much of the real instructions the generated text recovers, along the longest shared sequence of words. Distinct [39] measures something different again, the fraction of the generated word sequences that are unique, which is a measure of variety rather than of accuracy and guards against a model that says the same safe thing every time. All three are computed on the dataset's official test split. Two honest points carry over from Chapter 4: the figures are from a 2,000-recipe sample of the test set with a full run still to come, and perplexity, a fourth common measure, is left out because the models being compared use different tokenizers and their perplexities are not on the same scale.

**Figure 19. Generalisation of the recipe generator.** *[Insert docs/figures/nutrition/10_generalization_gap.png]*

Figure 19 shows the gap between the generator's training and validation loss at each checkpoint, and the gap stays slightly negative throughout, which means the model does no better on the data it trained on than on data it has not seen, the clearest sign that the result is not an artefact of overfitting.

The deterministic meal planner is not evaluated by a learned metric, because there is nothing learned in it to measure; it is evaluated by whether it keeps its guarantee. The relevant numbers are the share of planned days that land inside the calorie band and the closeness of the planned macronutrients to their targets, both reported in Chapter 6, together with the fact that no plan in testing contained an excluded ingredient. For a deterministic system, a guarantee that holds across many profiles is the evaluation.

Taken together, 5.1 and 5.2 describe a system that is tested for correctness and honesty and evaluated by the same yardsticks as the work it builds on. With that in place, the results themselves can be read plainly, which is the subject of the next chapter.
