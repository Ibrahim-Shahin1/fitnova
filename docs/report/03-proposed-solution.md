# 3 Proposed Solution

This chapter describes the proposed solution at the design level, before the implementation detail of Chapter 4. It starts with the solution methodology, the three pipelines and the way they fit into one system, then sets out the functional and non-functional requirements, and finishes with the design of each pipeline and the data that flows through it. The aim here is the shape of the system and the reasons behind it, not the code, which comes next.

## 3.1 Solution Methodology

FitNova is one backend service that hosts three independent modules behind a single application. A user provides a profile, the backend loads the three modules at startup and keeps them ready in memory, and each module answers the requests that belong to it through its own endpoints. The modules do not depend on each other to run, so a failure in one does not take the others down, but they are tied together by two things: the user, whose profile and goal are the common starting point, and a single design principle that shapes all three. That principle is to put a deterministic, rule-based core wherever correctness matters, and to let a language model speak only on top of a result that is already correct. The planner can only choose real programs and real exercises, the nutrition engine computes every number with fixed formulas, and the form models output a measured probability against a fixed threshold. A language model then explains the workout plan and the meal plan in readable words, but it is never the thing that decides them.

Figure 2 shows how the parts fit together. The user and the client app sit at the top, the backend in the middle holds the three pipelines side by side, and the datasets that each pipeline was built on sit at the bottom. Reading each column from top to bottom gives the flow of one feature, and the three columns share only the backend and the user, which is the level at which the system is integrated.

Two things are worth reading off the diagram. The first is that every pipeline ends in a deterministic step, the validated plan, the verified meal plan, and the thresholded detection, so the output a user sees has already passed a fixed check before any model's opinion is attached to it. The second is that the language models, drawn as the crews, sit to the side of the main flow rather than in the middle of it. They receive a finished result and add words; they do not stand between the data and the decision. The rest of this section walks down each of the three columns in turn.

The fitness planning pipeline is built as three layers, in the spirit of a hybrid recommender that does not rely on any single technique. The first layer is a content-based filter that scores every program in the catalogue against the user profile with four weighted rules, experience level, workout type, session length, and weekly frequency, and keeps the fifty best [7]. The second layer is the learned one. Because a brand new user has no history for a collaborative model to read, the system first finds the most similar of the 973 known users by cosine similarity on the profile, then uses a Neural Collaborative Filtering model, the method of He et al., to re-rank the fifty candidates for that surrogate user [2]. The two signals are blended, with the user's stated intent kept as the dominant sort key so that a plan always matches the goal the user asked for. The third layer turns the chosen program into a readable seven-day plan. A small crew of language model agents, a Profiler, a Generator, a Critic, and an Optimizer, drafts and refines the plan, but it may only use exercises drawn from the chosen program, and a deterministic validator checks the result against the user's training days, equipment, and injuries and repairs anything that breaks a rule. An invented exercise can not survive this step, because anything not in the dataset pool is dropped.

The form correction pipeline takes a different kind of input, a short video or a single image of a lift, and turns it into a yes or no for each named error. The video errors, the knees caving inward and the knees travelling too far forward in a squat, and the elbows and the knees in an overhead press, are read by an R(2+1)D-18 three-dimensional convolutional network [11], and the single depth error in a squat is read by a ResNet-18 image network [10]. Each clip is sampled to thirty-two frames, cropped, and normalised the same way the network was trained, then passed through a small ensemble of models trained from different random seeds, whose probabilities are averaged for a steadier answer. The averaged probability for each error is compared with a threshold that was tuned on the validation data, and the error is reported only when the probability clears it. For a recorded clip the whole repetition is judged at once, and for the live camera path a light motion-energy step, which needs no pose estimate, watches the movement and fires the model at the moment a repetition ends. The same models also drive a benchmark inspector, which runs them on the dataset's own test clips and shows the result next to the expert ground truth, so the output can always be checked.

The nutrition pipeline is the clearest example of the deterministic-first principle. It begins with a fixed calculation. From the user's weight, height, age, and sex it computes a resting metabolic rate with the Mifflin-St Jeor equation, multiplies it by an activity factor to get the daily energy need, adjusts that for the goal of losing, maintaining, or gaining, and splits the result into protein, fat, and carbohydrate targets, all with set formulas and safe floors [14]. A selector then searches a cleaned pool of about 167,000 Food.com recipes for items that fit the calorie target and the macro ratio and respect the user's allergies, and a planner arranges the chosen recipes into a day, or a week, of meals and runs a final check that the totals land on target and that nothing forbidden slipped in. Only after all of this does a second crew of language model agents, a Dietitian, a Composer, a Critic, and a Coach, add a plain-language explanation, day themes named from the real recipes, a quality note, and practical tips. The crew never picks a food or moves a number, so a broken calorie total or an invented recipe is impossible by design [4]. A separate DistilGPT-2 model writes step-by-step cooking instructions for a recipe when asked, which is a reproduction of a published generation task and is kept apart from the part of the system that has to be correct.

The three pipelines are connected by a shared shape rather than by a shared model or a shared dataset. Each one is grounded in a public dataset, each one keeps its numbers and its choices inside a deterministic core, each one is measured with the metric its source work used, and each one only lets a language model speak once the result is already settled. The planning and the nutrition features lean on this most heavily, because they produce something a user will act on, and the form feature adds to it the discipline of reporting a raw probability against a fixed line rather than a softened verdict. The sections that follow turn this methodology into concrete requirements and a detailed design.

## 3.2 Functional and Non-functional Requirements

This section states what FitNova has to do and the qualities it has to have. The functional requirements are the behaviours a user can ask for, and the non-functional requirements are the standards those behaviours must meet, the most important of which is that the system never shows a number or a result it can not stand behind.

Figure 3 is the use-case view of the platform. There is a single actor, the user, who works with one application that fronts all three modules. The user is the only actor, because FitNova has no second human role in the loop, no separate trainer or administrator, and the language models inside the system are services rather than actors, so they never appear on the diagram and never act on their own.

**Figure 3. FitNova use-case diagram.** *[Insert the use-case diagram drawn from the specification provided with this section.]*

The use cases fall into a small account layer and the three modules. In the account layer the user registers, logs in, and creates the profile that the planning and coaching features read from. In planning the user sets a goal, generates a seven-day plan, views the schedule, marks exercises and days as done, and can talk to an AI coach. In form correction the user uploads a lift or opens a benchmark clip and reads the honest per-repetition result. In nutrition the user gets calorie and macronutrient targets, generates a meal plan, reads the recommendations, asks for cooking instructions, and can adjust the plan. Everything passes through one backend, and nothing here needs the three modules to talk to each other, which matches the loosely-coupled design of Section 3.1.

The functional requirements run from the account layer outward, because every other feature reads the profile it produces. The user registers, logs in, and creates a profile that holds the training and body details the rest of the system needs. That profile is gathered in two ways that suit different users. A direct form lets a user fill in the fields, and a conversational intake lets a user describe their training in plain language, from which the system pulls out the three parameters the recommender needs most, the experience level, the session length, and the weekly frequency. The two paths meet in the same profile, so a user can begin with a short chat and never open a form.

Planning is the first feature built on that profile. The user asks for a seven-day plan, and the system has to produce one that fits the profile and, above everything, the stated goal, so that a plan for losing weight and a plan for gaining muscle come out clearly different. The plan has to be made only of real exercises from the dataset, and it has to be checked against the user's available training days, their equipment, and any injuries they listed, so that what comes back is always something the user can actually do safely. Around the single plan, the user can read the schedule day by day, mark exercises and whole days complete so the app tracks the week's progress, and hold a conversation with an AI coach that answers questions and, when asked, starts a fresh plan from the details it has gathered.

Form correction has the plainest contract of the three, and that is deliberate. The user uploads a squat or an overhead-press video, or opens a squat-depth image, and the system returns, for each repetition it finds, the raw confidence for every named error, the threshold that confidence is judged against, and whether the error was detected, along with a thumbnail of the repetition and a count of repetitions. There are no severity words and no coaching sentences, because the dataset labels are yes or no and anything richer would be made up. The same feature lets the user open the dataset's own benchmark clips and see the model's output set against the expert ground truth, which turns a feature that would otherwise have to be trusted into one that can be checked. And because the models only hold up on footage like their training data, the feature has to warn the user when a clip falls outside that domain and steer them toward a side-on, full-body, landscape shot.

Nutrition mirrors planning, but for food. From the profile the system computes a calorie target and a split into protein, fat, and carbohydrate, then builds a meal plan from real recipes that meets those numbers and respects the user's diet and allergies. The plan carries a guarantee that its totals land on target and that no excluded ingredient is present, and only after that does the system add a readable explanation, a name and a short theme for each day taken from the actual recipes, a quality note, and a few practical tips. The user can ask for full step-by-step cooking instructions for any recipe, and can adjust a finished plan by swapping a meal or adding an ingredient to avoid, with the change carried out by the deterministic planner so the plan stays correct after the edit.

All of this reaches the user through one backend, which exposes the features over ordinary request-and-response calls, a streaming channel for the progressive and live parts, and a websocket for the live camera path, and which also serves the media the features need. The behaviours above are only worth anything if they hold to a set of qualities, and this is where most of the project's character sits. The first and most important quality is that the system does not fabricate. This is built into the structure of every module rather than being a matter of tone or a guideline to follow. In planning, the language model crew may only assemble a plan from a pool of real exercises, and a deterministic validator drops anything outside that pool, so an invented movement can not reach the user. In nutrition, every number comes from a fixed formula and every recipe is chosen by a deterministic selector and re-checked by a verifier before any language model is allowed to speak, so a wrong calorie total, or a recipe that was never in the dataset, is impossible by construction. In form correction, the services hand back a measured probability and a threshold and nothing else, so there is no opening for an invented verdict. The whole system is arranged so that the parts which could make something up are kept away from the parts that decide anything.

The second quality is evaluation fidelity. Every number this report puts forward about model quality is computed on the official train, validation, and test split of the dataset it belongs to, with the same metric the source work used, and it can be reproduced from a result file kept in the repository. This matters because the project's central claim is a comparison with published work, and a comparison only carries weight when it is measured the same way and can be repeated.

The third quality is performance good enough to feel interactive. The form models run a small ensemble for each repetition, and the squat path was also exported to a faster runtime so that a single repetition is scored in roughly a second; the heavier plan generation runs in its own process under a time limit; and because the backend sits on a single event loop, the heavy model calls are pushed onto a worker thread so that one user's inference does not freeze the server for everyone else.

The fourth quality is graceful degradation. A missing model file, or a missing key for the language models, has to leave the system working rather than crashing. When the form weights are absent the service returns a neutral, clearly marked result; when there is no language-model key the planning and nutrition features fall back to deterministic template explanations that still carry the correct numbers; and every live session is given its own isolated state so that one user's stream can not disturb another's.

The fifth quality is honesty about the limits, which is an unusual thing to write into a requirement but is central here. The form models are trained on one kind of in-the-wild footage and are close to random on a casual front-facing phone clip, and the system is required to say this plainly, to mark input that falls outside that domain, and never to dress a weak result up as a confident one.

The remaining qualities are more ordinary but still required. The user's data endpoints are protected by authentication and the media endpoint is guarded against path traversal. The scope stays non-clinical, and allergens are removed by construction rather than by warning. The model directories and the ensemble sizes can be set from the environment, so the system moves between machines without code changes. The datasets are used within their research and licensing terms. And a single source of truth for preprocessing keeps the served model identical to the one that was trained, which is the strongest guard against a model that scores well in an evaluation and then behaves differently once it is deployed. Table 4 collects these as numbered requirements.

**Table 4. Non-functional requirements.**

| ID | Requirement |
|---|---|
| NFR-1 | No fabrication: the system never presents an invented exercise, number, or recipe; correctness is enforced by deterministic gates before any language model runs |
| NFR-2 | Evaluation fidelity: every reported metric uses the source work's own metric on the dataset's official split and is reproducible from a committed result file |
| NFR-3 | Interactive performance: per-repetition form inference and plan or meal generation finish in a time fit for interactive use, and CPU-bound inference is offloaded so the server stays responsive |
| NFR-4 | Graceful degradation: a missing model or API key falls back to a safe default rather than failing hard, and each live session is isolated |
| NFR-5 | Honesty about limits: the form feature states that the models are reliable only on in-the-wild dataset footage and weak on casual phone video, and never hides this |
| NFR-6 | Safety and security: user-data endpoints are authenticated, media access is protected against path traversal, allergens are excluded, and the scope is non-clinical |
| NFR-7 | Configurability and portability: model directories and ensemble sizes are set by environment variables, and the system runs on the documented local stack |
| NFR-8 | Data and licensing: Fitness-AQA is used for research only, Food.com under its terms, and any vendored code keeps its original licence |
| NFR-9 | Training and serving parity: a single source of truth for preprocessing keeps the served model identical to the one that was trained |

Taken together, these qualities are the real specification of FitNova. The behaviours in Table 3 describe a fairly ordinary fitness application; it is the qualities in Table 4, and the no-fabrication property most of all, that separate the version built here from one that would simply produce plausible output. The design in the next section is shaped to meet them.

## 3.3 Design

This section gives the detailed design of the system, building on the methodology of Section 3.1. It first describes the platform as a stack of layers, then walks down the design and the data flow of each of the three pipelines, with a figure for each, and ends with the backend that ties them together and the data and the models that sit behind them.

FitNova is built as four layers stacked on each other. At the top is the client, a mobile application that collects the user's input and shows the results. Below it is the backend, a single service that receives every request and routes it to the module it belongs to. Below that is the service layer, the recommender, form, and nutrition code, which is loaded once when the backend starts and then kept in memory for the life of the process, so that no model is read from disk on a per-request basis. At the bottom is the data and model layer, the datasets, the trained model files, and the cleaned catalogues, which the services read from but never change while the system is running. The overall shape of this stack was given in Figure 2, and the design below fills in the two middle layers, the backend and the services.

The workout planner has the most clearly layered design in the system, and Figure 4 draws it from the user profile at the top down to the finished plan at the bottom. The figure is worth reading before the description, because the vertical order of its boxes is exactly the order in which a request passes through the pipeline.

**Figure 4. Workout-plan recommender pipeline.** *[Insert docs/figures/recommender/recommender_architecture.png]*

The flow begins with the user profile, with the conversational intake filling in the three parameters it can extract, the experience level, the session length, and the weekly frequency. The first layer is a content-based filter that scores every one of the 3,048 programs in the catalogue with a weighted four-rule score and keeps the fifty that fit the profile best. The second layer is the learned one, and the cold-start box in front of it solves the problem that a new user is unknown to a collaborative model: the system finds the nearest of the 973 known users by cosine similarity and borrows that identity, then the Neural Collaborative Filtering model re-ranks the fifty candidates for it [2]. The blended score that comes out of this layer mixes the learned score, the content score, and the user's intent, with the intent kept as the strongest signal so the plan never drifts off the user's goal. The third layer hands the chosen program to the language model crew and the deterministic validator described in Section 3.1, and the pipeline ends in a plan made only of real dataset exercises. The panel on the right of the figure lists the data behind all of this, the 2,598 real and 450 synthetic programs, the 973 users, and the 809,439 synthetic interactions that the model in the second layer was trained on, with the arrow into that layer making the dependency clear.

The form-correction module is built from two models, one for each of the two kinds of input it has to read, and Figure 5 shows the two methods side by side. The left branch is for the errors that only make sense in motion, and the right branch is for the one error that can be read from a single still frame.

**Figure 5. Form-error detection, two-method architecture.** *[Insert docs/figures/methodology_diagram.png]*

On the left, the video errors, the two squat errors and the two overhead-press errors, are handled by a Motion-Disentangling self-supervised stage that learns from the structure of the barbell's path through a repetition, feeding an R(2+1)D-18 backbone that reads thirty-two frames at a time and ending in a multi-label head that reports the two co-occurring errors of each exercise together [3], [11]. On the right, the single depth error of a squat is handled by a Cross-View Cross-Subject pose-contrastive stage feeding a ResNet-18 image backbone and a single binary head [10], [25]. Both branches meet at the bottom of the figure at the same place, the dataset's official train, validation, and test splits, where each is scored with the per-error F1 against Parmar et al. The design at serving time follows the same split. A recorded clip is decoded to thirty-two evenly spaced frames, cropped and normalised exactly as the network was trained, then passed through a small ensemble of separately trained models whose probabilities are averaged, and each error is reported only when its averaged probability clears the threshold tuned on the validation data. A whole uploaded clip is treated as a single repetition, which fits the way the dataset was collected, while the live camera path adds a light motion-energy step that watches the movement with no pose estimate and fires the same models when a repetition ends. The benchmark inspector reuses these services unchanged and simply runs them on the dataset's own test clips so the output can be placed beside the expert ground truth.

The nutrition module is designed as a deterministic core wrapped in a thin language layer, and its data flow, drawn in Figure 6, is the clearest single picture of the no-fabrication principle in the whole system.

**Figure 6. Nutrition pipeline data flow.** *[To be drawn from the specification provided with this section.]*

Reading the figure from top to bottom, the user's body details and goal enter a deterministic engine that computes a resting metabolic rate with the Mifflin-St Jeor equation, scales it by an activity factor into a daily energy need, adjusts it for the goal, and splits it into protein, fat, and carbohydrate targets [14]. A selector then searches the cleaned pool of about 167,000 Food.com recipes and scores each one on how well it fits the calorie target and the macro ratio, while removing anything that breaks a diet rule or contains an excluded ingredient [4]. A planner places the chosen recipes into the slots of a day, or a week, and then a verify step re-checks the whole plan against the calorie band, the macro targets, and the allergen list. This verify step is drawn as a gate, because it is the point at which correctness is guaranteed: only a plan that passes it is allowed through. Only after the gate does the four-agent crew add its explanation, its day themes, its quality note, and its tips, and the figure draws the crew to the side of the main line on purpose, because it annotates a plan that is already settled and can not change a number or a food.

All three pipelines live inside one backend, and its design has to hold several things together at once. When the backend starts it loads every service one time and attaches it to a shared application state, so the recommender, the language adapters, the three form services, the nutrition crew, and the benchmark catalogue are each built once and then reused. The backend speaks three transports: ordinary request-and-response calls for the stateless features like generating a plan or computing nutrition targets, a server-sent event stream for the features that report progress as the agent crews work, and a websocket for the live camera path, where each connection is given its own isolated session so that one user's stream of frames can not mix with another's. Two machine-learning runtimes run inside the same process, because the form models are in PyTorch and the existing recommender is in TensorFlow, and the backend is designed to load both without either interfering with the other. One part is deliberately pushed out of the main process: the workout-plan crew runs in a separate, isolated environment and is reached through a short-lived subprocess, which keeps the heavy agent framework and its dependencies away from the rest of the backend, while the lighter nutrition crew runs in the main process directly. Because the whole server runs on a single asynchronous event loop, the model calls, which are the slow part, are pushed onto worker threads so that one user's inference does not block everyone else's requests.

Behind the services sits the data and model layer, which is read-only while the system runs. The planner reads a catalogue of 3,048 programs and a trained Neural Collaborative Filtering model with its two pretrained component models, together with the normalisation statistics used to encode a profile. The form module reads three small sets of trained weights, one for each exercise family, with the squat set also exported to a faster runtime for quicker inference. The nutrition module reads the cleaned pool of about 167,000 recipes and the small distilled language model that writes cooking instructions on request. None of these files is written during a request, which is part of why the same input always produces the same output and why the system can be reasoned about and tested. The implementation of each of these pieces, the datasets and how they were prepared, the exact model architectures, and the training that produced the weight files, is the subject of the next chapter.
