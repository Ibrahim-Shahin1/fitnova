# 4 Implementation

This chapter is the concrete build of the three pipelines, where the design of Chapter 3 turns into datasets, model code, training runs, and serving. It is the longest chapter, and it is organised pipeline by pipeline. This section covers the fitness planning pipeline. The form correction pipeline follows, together with an honest account of the earlier designs that were built on other datasets and then dropped, and the nutrition pipeline comes last. The stack is shared across the three: the recommender model is in TensorFlow, the form models are in PyTorch, the language parts use a hosted GPT-4o-mini model through small agent crews, a small distilled language model writes recipe text, and everything is served from one FastAPI backend. Every number reported in this chapter is taken from a result file kept in the repository, so the figures can be reproduced rather than taken on trust.

## 4.1 Fitness Planning Pipeline

The fitness planning pipeline is the three-layer recommender of Section 3.3, and this section describes how it is built. It starts with the data, then takes each of the three layers in turn: the content-based filter, the neural collaborative filtering model, and the language model crew that writes the final plan.

### Datasets

The recommender is built on two public Kaggle datasets and a third set of interactions that the project generated itself. The first dataset is a fitness-program dataset in which each row is a single exercise inside a named program. The build step groups these exercise rows by program title, so every unique title becomes one program record carrying its training goal, its difficulty level, its program type, and the full list of its exercises by week and day. The difficulty of a program is taken as the easiest level it lists, and its type, whether it is mainly strength, cardio, yoga, or interval training, is inferred from keywords in the title and the exercise names. This collapse produces 2,598 real programs.

Because those real programs lean heavily toward strength training, the catalogue is padded with 450 synthetic programs, 150 each of yoga, cardio, and interval training, so the minority types are represented well enough for a model to learn them. The final catalogue is 3,048 programs, 2,598 real and 450 synthetic.

**Figure 7. Programs catalogue EDA.** *[Insert docs/figures/recommender/recommender_programs_eda.png]*

Figure 7 shows the make-up of this catalogue. The training-goal panel shows how strongly the real data leans toward bodybuilding and the strength goals, with the lighter goals like flexibility and cardio health appearing only a few dozen times each. The experience-level panel shows the catalogue weighted toward beginner and intermediate programs, and the program-type panel shows the effect of the synthetic padding, with strength still dominant but yoga, cardio, and interval training each now clearly present. The time-per-workout panel shows most programs sitting between 40 and 90 minutes. This imbalance is the reason the interaction data and the way the model is evaluated were handled with care.

The second dataset is a gym-members dataset of 973 people, each described by age, sex, height, weight, body-mass index, the length of a typical session, how many days a week they train, their main workout type, and an experience level. This is the dataset the recommender treats as its set of known users.

**Figure 8. Gym-members dataset EDA.** *[Insert docs/figures/recommender/recommender_users_eda.png]*

Figure 8 shows the spread of these members. They run from 18 to 59 years old with a mild concentration in the early twenties, the body-mass index is centred a little under 25 with a long tail upward, the two sexes are close to even, and the four workout types and three experience levels are all well represented. There is nothing unusual in the distribution, which makes it a reasonable basis for the cold-start matching described later.

The third set is the one that has to be described carefully, because it is not real. A collaborative filtering model needs a record of which users liked which items, and no such record exists for this project, since there is no deployed app collecting real choices. The interactions were therefore generated. For each of the 973 users and each of the 3,048 programs, a compatibility score is computed from a weighted rule, leaning mostly on how well the program's type matches the user's preferred type, with smaller contributions from experience, session length, and weekly frequency, and a small amount of random noise is added. The scored matrix is then turned into yes-or-no interactions by choosing a cut-off that leaves the matrix about 94 to 96 percent empty, the kind of sparsity a real recommendation dataset has, and four negative examples are sampled for every positive one. The result is 809,439 interactions, of which 161,948 are positive, at 94.5 percent sparsity.

**Figure 9. Synthetic user-program interactions EDA.** *[Insert docs/figures/recommender/recommender_interactions_eda.png]*

Figure 9 shows this generated data, and it is labelled synthetic on its face for the same reason it has to be flagged here. Because the interactions were produced from a rule, a model trained on them is, at best, learning to reproduce that rule. The hit-rate and ranking scores reported in Chapter 6 measure how well the neural model reconstructs the synthetic compatibility pattern, which is a fair test of the modelling method but is not evidence about real-world recommendation quality, which would need real user behaviour to judge. One detail matters for honesty: the weights used to generate the interactions, which lean heavily on workout type, are deliberately not the same as the weights the serve-time content filter uses, which lean on experience, so the learned model is not simply handed the exact rule the first layer already applies.

### Layer 1: content-based filtering

The first layer scores every program in the catalogue against the user profile with a weighted sum of four rules: how well the program's difficulty matches the user's experience, weighted 0.35; how well its type matches the user's preferred type, weighted 0.30; how close its session length is to the user's, weighted 0.20; and how close its weekly frequency is, weighted 0.15. Each rule is a small lookup or a banded score rather than a raw difference, so a near match scores well and a far one scores zero. On top of the weighted sum, a tie-breaker rewards a program whose goal exactly matches the user's stated intent, which keeps the goal visible even when two programs otherwise score alike. The 50 highest-scoring programs are passed to the next layer. This kind of additive content-based scoring follows the content-based recommender tradition [7]; the exact weights are the project's own choice rather than a published formula.

### Layer 2: neural collaborative filtering

The second layer is a Neural Collaborative Filtering model, built as He et al. describe it [2] and implemented in TensorFlow [30]. It has two halves. One half, generalised matrix factorisation, gives each user and each program a 16-dimensional vector and multiplies them element by element, which is the neural form of classic matrix factorisation [8]. The other half, a multi-layer perceptron, gives each user and each program a separate 32-dimensional vector, joins them, and passes them through a tower of fully connected layers of sizes 64, 32, 16, and 8. The two halves are joined at the end, the 16-dimensional product from the first and the 8-dimensional output from the second, and a single unit reads a score from the combined 24 numbers.

The model is trained in the three stages the original method prescribes. The two halves are first trained on their own, each for 20 passes over the data with the Adam optimiser, then their learned weights are copied into the combined model, whose final layer is started as a balanced mix of the two, and the whole model is fine-tuned for 10 more passes with plain stochastic gradient descent, keeping the version that scored best along the way. It is evaluated the way the original paper evaluates it, by holding out one positive program per user and ranking it against 99 programs the user did not interact with, then measuring how often the held-out program lands in the top 10, the hit rate, and how high it sits when it does, the normalised discounted cumulative gain. On this test the combined model reaches a hit rate at 10 of 0.9270 and a ranking score of 0.7469, ahead of either half on its own, and the full comparison is shown in Chapter 6. These numbers carry the caveat from the data section: they show the method works on the data it was given, and that data is synthetic.

At serving time a new user, who is not one of the 973 known users, is first mapped to the nearest known user by cosine similarity over the profile, so the model has an identity to score with. The model's score for each of the 50 candidates is then blended with the content score and the user's intent, weighted 0.45 to the model, 0.25 to the content score, and 0.30 to the intent, and the intent is also used as a hard tier, so a program that matches the user's goal always outranks one that does not, whatever the blended score.

### Layer 3: plan assembly and validation

The third layer turns the single chosen program into a written seven-day plan. Before this, the user's three core parameters can be gathered through a short conversation: the hosted GPT-4o-mini model reads the user's messages and pulls out the experience level, the session length, and the weekly frequency, and reports the intake as finished only once all three are present. The plan itself is written by a crew of four agents on the same model, a Profiler that reads the profile, a Generator that drafts the plan, a Critic that judges it, and an Optimizer that fixes it. The crew is given a pool of exercises taken only from the chosen program, topped up where a training split needs a movement group the program is short on, but never with anything from outside the dataset. The Critic and the Optimizer loop for up to three rounds, and the loop stops as soon as a deterministic check reports no hard violations.

That deterministic check is the real guarantee. It counts a violation whenever the plan has the wrong number of training days, places an exercise on a day its movement group does not belong to, asks for equipment the user does not have, or includes a movement that clashes with a listed injury, and it repairs these by dropping or replacing the offending exercise from the dataset pool. The Critic's own score is capped by this count, so the language model can not award a high score to a plan that still breaks a rule. The crew is built with CrewAI, a framework for orchestrating several language model agents in sequence, and it runs in a separate, isolated environment reached through a short-lived subprocess, which keeps that framework's heavy dependencies away from the rest of the backend. If the language model is unavailable, a deterministic template still produces a valid plan from the same pool. The plan that reaches the user is therefore always made of real dataset exercises and always passes the rules.

## 4.2 Form Correction Pipeline

The form correction pipeline is the deepest technical work in the project, and it was rebuilt from the ground up on the Fitness-AQA dataset and method after the earlier designs described at the end of this section were dropped. It detects five named errors across three exercises: in the squat, the knees caving inward and the knees travelling too far forward; in the overhead press, the elbows flaring and the knees bending; and, from a single image, a squat that does not reach depth. The four motion errors are read from video by a three-dimensional convolutional network, and the depth error is read from a still frame by an image network. This section follows the build in the order it was done: the dataset and what is in it, the supervised baseline, the self-supervised pretraining that improves it, the image model, the ensembles and serving, and finally an honest account of the approaches that were tried first and rejected.

### Dataset and exploratory analysis

The dataset is Fitness-AQA, the in-the-wild gym dataset of Parmar et al. [3]. Its clips were collected from public video platforms and show real people training in real gyms, with all the camera angles, clothing, lighting, and partial occlusion that this implies, and each clip is annotated by expert trainers for the specific errors it contains. The project uses the dataset's three exercises, the back squat, the overhead press, and the squat seen as a still image, with the official train, validation, and test splits taken exactly as released, so that every number can be compared straight against the published work.

Table 5 sets out the five errors and how they break down. Two things stand out. The first is how rare some errors are: the inward-knee squat error is present in only about one clip in seven, and the elbow error in the overhead press in about one in four, while the forward-knee squat error is the opposite and shows up in two clips out of every three. A detector therefore has to find a needle for some errors and a haystack for others, which is exactly why the decision thresholds are tuned per error rather than left at one half. The second is that, in the squat, the two errors travel together: of the 232 clips with the inward-knee error, 192 also have the forward-knee error. Because they co-occur this strongly, the two squat errors are learned by one shared network with a two-output head rather than by two separate models.

**Table 5. Fitness-AQA errors used in FitNova, with class balance and official splits.**

| Error | Modality | Total | Erroneous (%) | Train / Val / Test |
|---|---|---|---|---|
| Squat knees-inward (KIE) | video | 1,623 | 232 (14.29%) | 1,136 / 243 / 244 |
| Squat knees-forward (KFE) | video | 1,623 | 1,109 (68.33%) | 1,136 / 243 / 244 |
| Squat shallow-depth | image | 3,611 | 1,584 (43.87%) | 2,542 / 529 / 540 |
| OHP elbows | video | 2,260 | 576 (25.49%) | 1,582 / 339 / 339 |

The video clips run at 30 frames per second and vary a good deal in length, the squat clips from 49 to 404 frames with a median around 111, and the overhead-press clips from 49 to 271 with a median around 107, so each one is later reduced to a fixed number of frames before it reaches a model. Alongside the small labelled sets, the dataset provides much larger pools of unlabelled clips, several thousand for each exercise, and these are what the self-supervised pretraining described shortly learns from.

**Figure 10. Fitness-AQA error class balance and the squat KIE/KFE co-occurrence.** *[Insert docs/figures/fitnessaqa_class_balance.png]*

Figure 10 draws the same picture. The left panel shows the percentage of erroneous examples for each error, making the gap between the rare inward-knee error and the common forward-knee error plain to see, and the right panel is the two-by-two table of how the two squat errors fall together, with the 192 jointly erroneous clips filling the bottom-right corner. The imbalance and the co-occurrence in this figure are the two facts that shaped the model design.

Because this imbalance runs through every error, the module handles it in a few specific ways rather than letting the rare errors be ignored. The training loss is class-weighted, so a positive example of a rare error counts for far more than a positive of a common one; for the squat, where the inward-knee error is rare and the forward-knee error common, the two weights work out at about 6.1 and 0.45, roughly the inverse of how often each error appears. The decision threshold for each error is then chosen on the validation split alone, never on the test split, so a scarce error is not lost simply because a default cut-off of one half happens to suit the common case. The self-supervised pretraining covered later in this section lifts the rarest errors the most, which is where a few hundred labels help least. And the final model for each exercise is a small ensemble of networks trained from different random seeds, whose averaged output is steadier on the rare classes than any single run. Together these keep the scarce errors visible instead of being swallowed by the common ones.

### The supervised baseline

Following the project's data-first principle, a plain supervised model was trained for each exercise before any self-supervised pretraining, so that the value of the pretraining could later be reported as a measured gain over a real baseline. The model is an R(2+1)D-18 network [11], implemented in PyTorch [31]: a residual 18-layer three-dimensional convolutional network that splits each spatio-temporal convolution into a spatial convolution followed by a temporal one, started from weights pretrained on the Kinetics-400 action-recognition dataset [32]. Each clip is reduced to 32 frames sampled evenly across its length, every frame resized so its short side is 128 pixels and then centre-cropped to 112 by 112 and normalised with the Kinetics statistics, which is exactly the input the backbone was trained on. Because the two squat errors co-occur, they share one backbone with a two-output multi-label head rather than two separate models, and the strong class imbalance is handled with a class-weighted loss that gives the rare positive examples more weight.

Trained this way, the squat baseline reaches a test F1 of 0.286 on the rare inward-knee error and 0.800 on the common forward-knee error, a macro average of 0.543, which already lands within about two percent of the published supervised result. But it overfits the small labelled set badly: over training the training loss falls from 0.83 to 0.07 while the validation loss climbs from 0.81 to 2.27, the plain signature of a model that has memorised a few hundred positive examples rather than learned the error. The overhead-press baseline behaves the same way. This overfitting, and not a hunch, is the concrete reason the project turned to the self-supervised pretraining described next, which gives the network a head start that a few hundred labels can not.

### Motion-Disentangling self-supervised pretraining

The fix for the baseline's overfitting is to give the network a useful starting point that does not depend on the few hundred labels, and that is what self-supervised pretraining provides. The method is the Motion-Disentangling task of Parmar et al. [3], a contrastive task that learns from the large pool of unlabelled clips with no error labels at all. It uses a piece of gym-specific domain knowledge: a repetition has a clear lowest point, the bottom of the squat or the bottom of the press, which can be found from the barbell's path with no human labelling, and each repetition is split there into two halves. The network is then trained, in the contrastive way that methods like SimCLR made standard [25], to pull together the representations that belong to the same repetition and push apart those from different ones, so that it learns what the motion of a real lift looks like before it is ever shown a labelled error.

The pretraining is sensitive to how the input is augmented, and getting that wrong makes it collapse, which is worth recording because the fix is instructive. With a mild set of augmentations the representations lose their variety, a measure of their effective spread falling from about 11.8 to 3.3, and a quick test that trains a simple classifier on the frozen features peaks at the fifth epoch and then gets worse, the tell-tale sign that the network has found a shortcut instead of learning the motion. The cure is to follow the paper's own recipe more closely and use a stronger set of augmentations, with one deliberate exception: rotation is left switched off, because rotating the frame would change the very knee angle that the inward-knee error depends on, and a task that learns to ignore rotation would also learn to ignore that error. With the stronger augmentations the collapse goes away. On the frozen features the simple classifier now reaches a macro score of about 0.57 against 0.43 for the plain Kinetics start, a gain of about 0.14, and almost all of that gain sits on the rare inward-knee error, whose score roughly doubles, which is exactly the error that a few hundred labels struggle with most.

**Figure 11. Motion-Disentangling pretraining health.** *[Insert docs/figures/ohp_ssl_curves.png]*

Figure 11 shows a healthy pretraining run, here for the overhead press. The contrastive loss falls smoothly, the measure of representation spread stays well above the collapse floor instead of sliding toward it, and the frozen-feature classifier climbs and then holds rather than peaking and dropping, all three the opposite of the collapse just described.

After pretraining, the network is fine-tuned on the small labelled set in the ordinary supervised way, but it now starts from features that already understand the movement. A single fine-tuned network still overfits eventually, so the run keeps the version from the epoch just before the validation loss starts to rise rather than the final one, and the deployed model for each exercise is a small ensemble of these fine-tuned networks trained from different random seeds, three for the squat and two for the overhead press, whose probabilities are averaged.

**Figure 12. Fine-tuning with early stopping.** *[Insert docs/figures/ohp_finetune_curves.png]*

Figure 12 shows why the early stop matters. Across the seeds the gap between training and validation widens past a certain epoch as the network begins to memorise, and the kept checkpoint is taken from before that point, so the deployed model is the one that still generalises rather than the one that has started to overfit.

The effect on the test scores is a clear, measured lift over the baseline. On the squat, the macro F1 rises from 0.543 to 0.6304, with the rare inward-knee error climbing from 0.286 to 0.4198 and the common forward-knee error from 0.800 to 0.8410, a gain of 0.087 that matches the published self-supervised result of 0.6262. On the overhead press, the macro F1 reaches 0.6622, with the elbow error at 0.4474 and the knee error at 0.8770, a gain of 0.050 over its own baseline that edges past the published 0.6502, mostly on the knee error. The decision thresholds, chosen on the validation split, come out at 0.614 and 0.385 for the two squat errors and 0.357 and 0.476 for the two overhead-press errors, which reflects how differently a rare and a common error sit. Test-time augmentation, which averages a model's output over small transforms of the input, was tried as a further step and then dropped, because it helped on the validation split and reversed on the test split, and a technique that does not hold on unseen data does not belong in the deployed model. The full comparison of these scores against the published work is laid out in Chapter 6.

### The image error: ResNet-18 with pose-contrastive pretraining

The fifth error, whether a squat reaches depth, is the one that can be judged from a single still frame rather than from motion, so it is handled by an image model instead of a video one. The model is a ResNet-18 [10], started from weights pretrained on ImageNet [33], and it is improved with the same idea as the video models, self-supervised pretraining, but in the form the dataset's authors designed for images, Cross-View Cross-Subject Pose Contrastive learning. The task builds triplets of frames in which an anchor pose is paired with the same pose seen from a different camera or performed by a different person as the positive, and a different pose as the negative, so the network learns a representation of body pose that does not depend on who is in the frame or where the camera is, which is exactly the kind of nuisance variation that wrecks a depth judgement in the wild [3], [25].

Two honest points belong with this model. First, the loss that was implemented is the one in the dataset's official code, a three-term distance-ratio loss, rather than the two-term loss written in the paper's equation; the two differ, and this report follows the code because the code is what the released results came from, but the deviation is stated rather than hidden. Second, the frames for pretraining were extracted from the unlabelled clips with care to avoid leakage: clips that overlap the labelled evaluation set were held out before extraction, leaving about 4,791 clips and some 581,503 frames to learn from, so no frame the model trains on can reappear at test time. Over a hundred epochs of this pretraining, a measure of how well the learned features separate the triplets rises from about 0.48, little better than chance, to 0.959.

**Figure 13. CVCSPC pretraining and fine-tuning for the depth error.** *[Insert docs/figures/shallow_squat_training_curves.png]*

Figure 13 shows this. The triplet measure climbs steadily through pretraining toward 0.959, the per-seed validation scores of the fine-tuned classifiers settle close together, and the small but real gain of the pretrained model over the plain baseline is visible at the end.

Fine-tuned and ensembled across three seeds in the same way as the video models, the depth model reaches a test F1 of 0.8902, a gain of 0.0152 over its own supervised baseline of 0.8750 and above the published result of 0.8694, with its decision threshold set at 0.395 on the validation split.

One detail of this model needs to be stated plainly, because it is easy to get backwards. The dataset's label 1 marks the deeper squat, the one that does reach depth, which was confirmed by checking the pose geometry of the labelled frames. The model is therefore a depth detector, read as a high score meaning the squat reached depth. The result is steady whichever way the convention is read: scored as it is the F1 is 0.8902, scored the other way it is 0.9050, and the balanced average of the two is 0.8976, so the model's quality does not hang on the direction of the label. Figure 14 shows example frames on either side of the label so the convention is unambiguous.

**Figure 14. Shallow-squat depth, example frames by label.** *[Insert docs/figures/shallow_squat_samples.png]*

Figure 14 places a few frames the dataset labels as reaching depth next to a few it labels as too shallow, which makes the convention concrete and shows the kind of in-the-wild frames the model has to judge.

### Ensembles and serving

The three models, the squat video model, the overhead-press video model, and the squat depth image model, are deployed as a serving layer inside the same backend as the recommender. Each is loaded once at startup and answers requests as a small ensemble, three networks for the squat and the depth model and two for the overhead press, with their sigmoid outputs averaged and compared with the per-error thresholds. For a recorded clip the upload endpoint decodes the video, reduces it to the 32 frames the model expects with the same crop and normalisation used in training, and treats the whole clip as one repetition, which fits the way the dataset clips were collected. The depth model takes a single frame instead. The live camera path adds a small step that watches the motion energy of the incoming frames, with no pose estimate at all, and triggers the model when a repetition ends, and each live connection is given its own isolated state.

For the squat model, the most used path, each network is also exported to the ONNX runtime, which runs the same computation about 1.6 times faster on the processor with the outputs matching the original to within about 2.4 parts in ten million, so the speed-up costs nothing in accuracy. A benchmark inspector reuses these exact services and runs them over the dataset's own test clips, 244 for the squat, 339 for the overhead press, and 540 for the depth model, showing each model's output beside the expert ground truth so the result can be checked rather than trusted.

There is one hard limit to state plainly, and it is the same limit the dataset's authors built their work around. These models are reliable on footage like the data they were trained on, real gym video shot from the side with the whole body in frame, and they are close to random on a casual, front-facing phone clip taken at arm's length. This is why the user-facing part of the form feature was reframed as a benchmark inspector rather than a general camera tool: the honest thing to ship is a system that demonstrates the measured result on the data it was measured on, and says so, rather than one that pretends to work on any video. The evaluation that produced all of these numbers, and the audit that checked the models are not simply overfitting, are the subject of Chapters 5 and 6.

### Approaches explored and rejected

The Fitness-AQA approach was not the first one tried for form correction. Several earlier designs came before it, and they are recorded here honestly, both because the report should be honest and because the reason they failed is what justifies the final choice. They all failed for one technical reason, which is worth stating once: each relied on labels that stood in for real form rather than being real form, and a model can only ever learn the labels it is trained on. Table 6 lists them, and the paragraphs that follow take each in turn.

**Table 6. Form-correction approaches that were investigated and rejected.**

| Approach | Data and labels | Why it was rejected |
|---|---|---|
| Pose plus multi-task temporal CNN | MediaPipe pose on Fit3D motion capture; synthetic corruption labels | Passed held-out motion-capture tests but collapsed on real phone video; its quality output never correlated with real quality above about 0.3 |
| Pose graph network (ST-GCN) | MediaPipe pose on Fit3D; synthetic angular-perturbation labels | Rated bad squats higher than good ones on real clips; the labels described the perturbation, not human form |
| Pose graph network on real video | ST-GCN on QEVD real clips; labels derived from coaching text by a keyword lexicon | Learned the per-exercise prior rather than the form, because the text labels tracked the exercise type |
| Vision-language model and distillation | A large multimodal model, with a distilled pose-plus-pixel student | Set aside on feasibility: the raw-video corpus was infeasible to move at the available upload speed, and the multimodal model needs several high-end accelerators and scores below the chosen method |

The first serious attempt reduced each video to a stream of body joints with a pose estimator [12] and fed that stream to a multi-task temporal convolutional network that tried to predict, all at once, which exercise was being done, how well it was done, where each repetition began and ended, and which joints were at fault. It was trained on Fit3D, the studio motion-capture dataset of fitness movements introduced with the AIFit work [23], with the form errors created synthetically by perturbing a clean repetition and labelling the joint that was moved. On held-out motion-capture data it looked healthy, reaching an accuracy near 0.88 on a held-out subject and a joint-error F1 around 0.61. On real phone video it fell apart: it labelled squats as burpees, its quality score sat near 0.85 whatever the form, the joint-fault channels flatlined to zero, and it detected no repetitions at all. Its quality output, the part meant to judge form, never correlated with real quality above about 0.3 across repeated retraining, well under the 0.65 it needed. The synthetic corruption and the studio capture had taught it a world that real video does not belong to.

The second attempt kept the pose idea but replaced the temporal network with a spatial-temporal graph convolutional network, the standard architecture for skeleton data [34], and labelled the data by perturbing joint angles rather than positions. It was tested directly on the thing that matters, whether it rates a good squat above a bad one, on real squat clips. It did the opposite: the average score it gave good squats came out about 0.05 below the average it gave bad ones, where a useful model would need a clear positive gap. The cause was the same as before in a new form. The labels were the ground truth of the perturbation, a known amount of corruption added to a clean signal, and the network learned to detect that corruption, which is not the same thing as judging a real person's form.

The third attempt changed the data instead of the model, moving the same graph network onto QEVD, a large dataset of real exercise videos annotated with natural-language coaching feedback [24], on the reasoning that real video would fix the transfer problem. It did not, because the labels were still a proxy. QEVD does not carry a clean yes-or-no for each form error; its feedback is free coaching text, and to train a classifier that text had to be turned into labels by a keyword lexicon. Because the wording of coaching feedback follows the exercise more than the fine detail of the form, the derived labels were correlated with the exercise type, and the network took the easy path and learned the per-exercise prior rather than the form. On the same good-versus-bad test it scored a gap of about +0.004, essentially zero. A hand-written geometric rule was attached as a stopgap, which only confirmed that the learned model was not carrying the load, and a later multi-label variant on the same data was shelved for the same labelling reason.

The last attempt before the change of direction went toward a large multimodal model that reads video and language together, with a plan to distill its judgements into a smaller student combining pose and raw pixels. This one was set aside less on accuracy than on feasibility. The raw-video corpus needed to train the student ran to hundreds of gigabytes, which at the available upload speed would have taken on the order of two weeks just to move, and the small subset that could be moved would have been too little to train a video network from scratch without overfitting. The large multimodal model itself, the same LLaVA-Video line discussed in the related work [27], needs several top-end accelerators to run and, when others have measured it on this very dataset, scores below the specialised method. So the direction was closed.

The common thread is plain in hindsight and is the justification for the final design. Every rejected approach learned from a label that was a stand-in for form, a synthetic perturbation or a word in a coaching note, and so every one of them learned the stand-in instead of the form and failed when it met a real lifter. The Fitness-AQA approach is the answer to exactly this: real in-the-wild video, labelled error by error by expert trainers, and scored with the same metric the published work uses. The numbers earlier in this section are what building on that footing produced, and Chapters 5 and 6 test them.

## 4.3 Nutrition Pipeline

The nutrition pipeline is the platform's third module, and it takes the design principle of Section 3.1 to its strongest form: every number and every food is decided by fixed rules, and a language model is allowed only to describe the result. This section covers the recipe data it draws on, the deterministic engine that turns a profile into calorie and macronutrient targets, the selector and planner that build a meal plan from real recipes and guarantee it is correct, and the crew of language agents that explains it. A separate piece of nutrition work, a reproduction of a published recipe-text generator, is described in the section after this.

### The Food.com recipe data

The recipes come from Food.com, the dataset used by Majumder et al. for their work on recipe generation [4]. The project uses the dataset's official splits, and they reconcile exactly to the figures in that paper: 698,901 training, 7,023 validation, and 12,455 test interactions, over 178,265 recipes and 25,076 users. For the meal-planning side of the module what matters is the recipes and their nutrition, so the recipes are cleaned into a runtime pool. Recipes whose stated energy falls outside a sensible range of 20 to 1,500 calories are dropped, as are recipes whose calorie figure does not agree with the sum of its macronutrients to within 30 percent, and exact duplicates. These three filters remove 7,942, then 3,320, then 5 recipes, leaving 166,998, about 93.7 percent of the aligned set. Each recipe's grams of protein, carbohydrate, and fat are recovered from the dataset's percentage daily values using the standard reference amounts, so the planner works with real macronutrient numbers rather than the dataset's coarse calorie band alone.

### The deterministic calorie and macro engine

The engine that sets a user's targets is a short chain of well-established formulas with no learning in it at all. It starts from the body-mass index, then computes a resting metabolic rate with the Mifflin-St Jeor equation [14], which adds 10 times the weight in kilograms and 6.25 times the height in centimetres, subtracts 5 times the age in years, and then adds 5 for men or subtracts 161 for women. That resting rate is multiplied by an activity factor, from 1.2 for a sedentary user up to 1.9 for an athlete, to give the total daily energy the user spends. The target is this total adjusted for the goal, lowered by 20 percent to lose weight, left as it is to maintain, or raised by 12 percent to gain, and then clamped to a safe floor of 1,500 calories for men and 1,200 for women, so a weight-loss target can never drop to something unhealthy. The target is split into macronutrients by rule as well: protein at between 1.8 and 2.2 grams per kilogram depending on the goal, fat at 0.9 grams per kilogram, and carbohydrate filling whatever calories are left, with the fat and then the protein trimmed back if there is no room left for carbohydrate. Because every step is a formula, the same user always gets the same numbers, and those numbers are correct by construction.

### Recipe selection and meal planning

Turning the targets into a plan is the job of a selector and a planner, and this is where the no-fabrication guarantee is actually enforced. The selector scores every recipe in the pool against a slot's calorie target and macronutrient ratio. A recipe more than twice the allowed tolerance away from the calorie target is removed outright, and the rest are scored on how close they sit, blended 60 percent on the calorie fit and 40 percent on how well the recipe's own split of protein, carbohydrate, and fat matches the target ratio. The ratio is used rather than the raw protein amount on purpose, so the selector does not simply pile up the highest-protein dishes and ignore everything else. Any recipe that breaks the user's diet or contains an excluded ingredient is removed first, matched on whole words so that excluding nuts, for instance, does not accidentally also remove nutmeg by a loose substring.

The planner splits the day into meals, breakfast, lunch, and dinner, with an optional snack, and gives each slot a share of the day's calories and the same macronutrient ratio. For each slot it asks the selector for its best candidates and picks the best one that has not already been used that week, so the plan keeps variety across the days. When the plan is assembled, a verify step checks it. It re-checks every meal against the user's allergens and diet as a strict pass-or-fail gate, and it recomputes the day's totals to report how closely they match the calorie and macronutrient targets. The allergen and diet check is the authoritative gate, and because the planner removes forbidden ingredients before it ever selects, a plan reaches this gate already clean. The calorie and macronutrient targets are correct by construction, since the engine sets them by formula and the planner only ever picks recipes inside the calorie window and the macro scoring, and the reported match shows how well that held: across contrasting user profiles the planned days land within about 10 percent of the calorie target on average, between 99.8 and 99.9 percent of the time.

### The annotation crew

Only once the deterministic plan exists does a language model see it, and even then only to describe it. A crew of four agents runs on a hosted GPT-4o-mini model: a Dietitian that explains the calorie and macronutrient targets in words, with an explicit instruction not to change any number; a Composer that gives the plan a title and a short theme for each day, drawn from the real recipe names and told not to invent recipes; a Critic that judges the plan's quality and variety; and a Coach that adds practical preparation and adherence tips. The Critic runs the verify step itself before it scores, and its score is hard-capped at a low value if the plan is not clean, so the language model can not call a broken plan good. What the crew returns is added alongside the plan, the day themes, the title, the rationale, the quality note, and the tips, while the actual days, meals, and totals come straight from the planner and are never touched. Hallucinated recipes and broken macronutrients are therefore impossible by design rather than something caught after the fact, and the whole feature still works with no language model at all, falling back to fixed template text that carries the same correct numbers. This crew runs inside the main backend process with direct calls to the language model rather than through CrewAI, unlike the workout-plan crew, so it does not need a second isolated environment for that framework's dependencies.

### Reproducing a published recipe-text generator

The nutrition module includes one piece of work that is a research result in its own right rather than a part of the meal-planning system: a reproduction of the recipe-instruction generation task from Majumder et al. [4], the same paper the recipe data comes from. The task is to write the cooking steps for a recipe given its name, its ingredients, and a calorie level, and the paper introduced several models for it. The aim here was to see whether a modern pretrained language model, fine-tuned on the same task and measured the same way, could match or beat those models.

The paper's official code was taken and brought up to date to run on the current version of PyTorch, with its original licence and headers kept intact, and its published models are used as the points of comparison. The new model is DistilGPT-2, a smaller, distilled version of the GPT-2 language model [35], fine-tuned on the task: the input is the recipe's name, ingredients, and calorie level, the target is the cooking steps, and the loss is computed only on the step tokens, so the model is graded on what it generates rather than on the prompt it is handed. It is fine-tuned for 2 epochs at a low learning rate and decodes greedily, with a rule that forbids repeating any three-word sequence so it does not fall into loops. One honest note belongs here: a faithful re-run of the paper's own older model was attempted as well, but it hit a training bug that leaked the target into the input, so it was discarded, and the paper's published numbers are used as the anchors instead of a re-run.

The model is evaluated on the official test split with the same overlap and diversity measures the paper reports, BLEU and ROUGE for how closely the generated steps match the real ones, and Distinct for how varied the wording is. Table 7 puts the result next to the paper's models. On a sample of 2,000 of the test recipes, the fine-tuned DistilGPT-2 beats all three of the paper's learned models on every one of the five measures, and against the paper's non-learned nearest-neighbour baseline, which simply retrieves an existing recipe's steps, it wins on four of the five, the exception being one diversity measure where retrieving a real recipe is naturally varied.

The validation loss falls smoothly from about 2.62 to 2.27 and stays a little below the training loss throughout, and it is still falling when training stops at two epochs, so the model is not overfitting and could likely be pushed a little further. Two limits have to be stated clearly so the claim is not read as more than it is. First, what this work matches and beats is the quality of the generated text; the paper's real contribution was something else, personalisation, generating steps conditioned on a user's cooking history and judged by whether the right user's recipe is recovered. This reproduction does not condition on a user and does not attempt that measurement, so the comparison is like-for-like on text quality and not on the thing the paper set out to do. Second, the numbers are from a 2,000-recipe sample of the roughly 11,700 test recipes, and a full-set run is the obvious next step that will replace them when it is done. Perplexity, a common language-model measure, is deliberately left out of the comparison, because the models use different tokenizers and their perplexities are not on the same scale, so comparing them would mislead. The record behind these numbers is a results file and a written summary kept in the repository rather than the exploratory notebook, which is kept only for provenance.
